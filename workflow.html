How the PublishFlow workflow works

This page describes, in technical detail, how the PublishFlow n8n node integrates with the TikTok API — for developers evaluating the integration and for TikTok's app review team.

1. What triggers a call to TikTok

The PublishFlow node only contacts TikTok when it executes as a step inside an n8n workflow that a user has built and run themselves — on a manual click, a schedule the user set, or an upstream event the user configured (for example, a new file landing in cloud storage). PublishFlow never calls the TikTok API on a schedule of its own, and never runs in the background outside of a user's workflow.

2. Scopes requested

The node requests the minimum scopes needed to publish a video and read back what happened to it. It does not request scopes for messaging, following, or reading a user's existing content library beyond what it publishes.

ScopeUsed for
user.info.basic Confirming which TikTok account is connected, and showing its display name in the n8n credential so users know which account a workflow will post to.
video.publish Uploading a video file and creating a post on the connected account, with the caption and privacy level set in the workflow.
video.list Looking up publish status and basic metrics for videos that this workflow itself published, so the node can report success or failure back into the workflow.

3. Authorization flow

PublishFlow uses TikTok's standard OAuth 2.0 authorization code flow with PKCE. A user starts authorization from inside n8n's credential screen, approves the requested scopes on TikTok's own consent page, and is redirected back to a fixed callback URL that n8n controls. n8n exchanges the code for an access token and refresh token and stores both as an encrypted credential — PublishFlow's own code never sees or stores the user's TikTok password.

Redirect URI: https://yourdomain.vercel.app/oauth/callback

Note for reviewers: replace the redirect URI above with the exact callback URL registered in your TikTok developer app before submitting for review — it must match exactly.

4. Data handling

A single workflow run passes the following data through PublishFlow, in memory, for the duration of that run:

  • The video file the user supplies as input — sent directly to TikTok's upload endpoint and not written to disk by PublishFlow.
  • The caption, privacy setting, and posting options the user configures on the node.
  • The TikTok-issued video ID, publish status, and metric values returned by TikTok, which are passed to the next node in the workflow and stored only where the user's own workflow chooses to store them (a database, spreadsheet, or log the user controls).

PublishFlow does not operate a server that retains video files, captions, or metrics after a workflow run completes. Long-term storage of any data is entirely under the control of the n8n instance the user runs and the destinations their workflow writes to.

5. Error handling

If TikTok returns an error — an expired token, a rejected upload, a rate limit — the node surfaces TikTok's error code and message as output, so the workflow can branch, retry, or alert someone. Expired access tokens are refreshed automatically using the stored refresh token before a call is retried.

6. Where the code runs

The node runs inside the user's own n8n instance, whether that's self-hosted or n8n Cloud. There is no PublishFlow-operated backend sitting between the user's n8n instance and the TikTok API.
